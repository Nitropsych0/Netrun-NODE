# A14 — широкий пул и поштучные с разбросом по всему блоку

Статус: дизайн, 2026-10-29. Затрагивает Netrun-NODE (radius, agent, bgp),
netrun-orchestrator (pergb_pieces, facts, sellable), бот/сайт (витрина).

## Решения владельца (2026-10-29)

1. Поштучный IP — **один адрес** (/128), разложенный с максимальным разбросом
   по всей подсети ноды, а не своя /64. Добавили /48 — разброс по /48,
   добавили /29 — по /29.
2. Пул **общий**: поштучные и ротационные берут адреса из одного пула, /64 под
   поштучный больше не резервируется.
3. Склад заранее нагенерированных прокси (`proxy_inventory`, refill,
   validation, пачки 3proxy) — легаси: поштучные создаются под запрос.
4. Гео продаётся поштучно **автоматически**, если у живой ноды есть блок
   **/56 или шире**. Сейчас на каждом гео /48.
5. **Несколько блоков на ноду** — сразу (например /48 + /29).

## Что сейчас мешает (A1/A13)

- Пул ноды = номера /64 (16 бит) внутри ОДНОГО /48 (`prefix` + `subnets
  0000-fffe`); `alloc.py` держит плотные массивы на 65 536 /64, явный список
  кандидатов, 16-битный `net` в sqlite (`nets`, `bindings`, `lists.piece_net`).
- Поштучный (A13-I) = своя /64 через `reserve_nets` (owner `perpiece`),
  ёмкость = свободные /64 − 5000. Отсюда «остаток» ~60 535 на гео.
- `netrun-bgp` анонсирует /32…/48; блоки уже /48 (BGP) не бывает — /49…/56
  приходят маршрутизированными от провайдера.

## Модель пула (нода)

- Факт `pool`: список блоков `[{"prefix": "2a0x:y::/29"}, {"prefix": "…/48"}]`,
  длина каждого 29…56, блоки не пересекаются. Старый вид (`prefix` /48 +
  `subnets`) принимается как один блок с тем же `lo..hi` — существующие ноды
  ничего не замечают.
- /64 идентифицируется абсолютной сетевой частью `n = addr >> 64` (для
  2000::/3 это < 2^63 — ложится в INTEGER sqlite). Глобальный индекс
  `g ∈ [0, T)`, `T = Σ 2^(64−len)`, через смещения блоков (отсортированы).
- Своя /64 ноды (`ffff` у легаси-/48) и найденные сканом /64 исключены, как
  раньше. Исключения — разреженные множества.
- Кандидаты неявные: «в пуле и не исключена». Случайный выбор = равномерный
  `g` с отбрасыванием исключённых. `last_used` — ограниченный разреженный
  LRU (вместо массива на 65 536). Логика «лучший из 4», A11, A12 не меняется.
- Миграция sqlite при первом старте: 16-битные `net` → `(prefix>>64) | net`.
  Запомненные static/sticky линии сохраняют адреса.

## Разброс (раздатчик поштучных)

Позиция `k = 0, 1, 2, …` → индекс `g`:

1. `B = ceil(log2 T)`, `r = bitreverse_B(k mod 2^B)` — порядок ван дер
   Корпута: 0 → начало, 1 → вторая половина, 2/3 → свободные четверти, …
2. Ключевой разворот поддеревьев: бит `i` (от старшего) =
   `r_i XOR (HMAC_SHA256(key, "netrun-a14-spread\0" ‖ B ‖ биты 0..i−1)[0] & 1)` —
   разброс сохраняется (каждое поддерево заполняется равномерно), но порядок
   не угадывается снаружи.
3. `g ≥ T` (сумма блоков не степень двойки) или /64 исключена → следующий `k`.
4. Адрес = `/64(g)` + `piece_iid(list_id)` (I3-тег, как в A13): два поштучных
   в одной /64 различаются хостовой частью, атрибуция трафика по тегу работает.

Блоки разных размеров получают поштучные пропорционально размеру (это и есть
максимальный разброс по адресному пространству).

**Кто считает.** Оркестратор, один раз при покупке: у него ключ адресов ноды
(`pergb_addr_key_enc`), её блоки (`node_prefixes`) и счётчик `k` на ноду
(`nodes.piece_seq`, под существующей per-node advisory-блокировкой). Адрес
пишется в `pergb_pieces.address` и дальше только передаётся. Поэтому добавление
блока (/29 к /48) **не двигает** адреса уже проданных — меняется лишь, куда
лягут следующие. Заказ берёт подряд идущие `k` → его штуки максимально
разнесены друг от друга.

## Контракт A14-P (поштучный на ноде)

- Запись списка `{kind:"piece", mode:"static", lineCount:1, pieceNet64:"<prefix>/64"}`.
  Оркестратор выбирает только /64 (по разбросу), нода дописывает хостовую
  часть — тег списка (`piece_iid`, как в A13). Два поштучных в одной /64 не
  совпадают никогда (тег зависит от id списка), поэтому проверка дублей не
  нужна; адрес приходит в ответе (`pieces.addrs`) и хранится в
  `pergb_pieces.address`.
- Отказы: `piece_net64_outside_pool` (ни в одном блоке, либо `ffff`/вне
  `subnets` основного /48), `piece_net64_excluded` (/64 основного /48, найденная
  сканом или зарезервированная — A13-I или пачка 3proxy) → оркестратор берёт
  следующий `k`. Проверка повторяется на каждом запросе: блок, ушедший из
  пула, даёт `list_off`.
- Нода сообщает в RADIUS только блоки, на которые есть локальный маршрут
  (агент перечитывает раз в минуту); `status.poolBlocks {configured, routed}`.
- `pieceNet` (A13-I) продолжает работать для уже проданных до их истечения.
- Ротационные не исключают /64 поштучных (общий пул) и пока берут адреса из
  основного /48 (этап 1б — из всех блоков).

## Продажа гео (оркестратор → бот/сайт)

- Гео продаётся поштучно, если есть нода, прошедшая текущий piece-гейт
  (`pergb_piece_gate_sql`), с блоком длиной ≤ 56. Ёмкость больше не считается:
  `stock_available` поштучного SKU = лимит заказа (`NETRUN_IPV6_MAX_QTY`) или 0.
- Бот: синхронизация витрины вместо `country_autoproduct` — товар страны
  создаётся/включается при «продаётся», скрывается при «нет»; ручное скрытие
  в админке (`manual_hidden`) синхронизация не перебивает. На сайте вместо
  числа — «в наличии».

## Маршрутизация блоков на ноде

- BGP-блоки (/29…/48): `netrun-bgp`, диапазон расширяется с /32…/48 до /29…/48.
- Маршрутизированные провайдером (/49…/56): новый список
  `NETRUN_POOL_ROUTED_PREFIXES` — только `ip -6 route replace local <P> dev lo`
  (AnyIP) + boot-юнит, без BGP.
- `netrun-proxy-guard` получает все блоки пула.

## Этапы

1. **Нода** (сделано, ветка `feat/a14-wide-pool`): `poolBlocks` в фактах,
   `pieceNet64`, схема 4, агент передаёт только маршрутизированные блоки и
   распознаёт их адреса.
   1б. Ротационные из всех блоков (разреженный раздатчик, 64-битные /64) — следом.
2. **Нода, маршрутизация** (сделано): `netrun-bgp` /29…/48,
   `NETRUN_POOL_LOCAL_PREFIXES` для провайдерских /29…/56.
3. **Оркестратор**: facts `pool` из `node_prefixes`; размещение `k` → адрес для
   новых поштучных; гейт продажи «блок ≤ /56»; ёмкость → лимит заказа.
4. **Бот/сайт**: синхронизация витрины поштучных, «в наличии».
5. **Выкатка**: одна нода → проверка (покупка, адреса, ротационные) → остальные
   по одной. Деплой нод и оркестратора — с подтверждения владельца.
6. **Уборка легаси** после истечения старых заказов (16 со склада, 6 A13):
   refill/validation, генератор пачек, `proxy_inventory`, `reserve_nets
   perpiece`, `pieceNet`.

## Отложено

- Разброс для static-линий одного ротационного списка (тот же механизм, но
  меняет правило выбора адресов новых линий) — после этапа 5, отдельно.
